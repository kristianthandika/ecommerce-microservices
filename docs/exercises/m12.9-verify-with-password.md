# m12.9 — Verifikasi Email dengan Tautan dan Password

## Yang akan Anda pelajari

- **Account pre-hijacking**: penyerang mendaftarkan email korban lebih dulu, lalu korban
  sendiri yang "mengaktifkan" akun milik penyerang.
- Mengapa tautan verifikasi saja tidak cukup, dan mengapa password saja juga tidak cukup.
- Membatasi tebakan password pada satu tautan, dengan penghitung yang **ter-commit**.

## Kondisi awal

`verifyEmail(token, _password)` di `services/auth-service/src/verification.ts`
mengaktifkan akun hanya dengan tautan; password diabaikan. Cari `TODO m12.9`.

```bash
git switch starter/m12.9-verify-with-password
npm ci && npm run build:packages
npm test --workspace=services/auth-service
```

Tes yang gagal:

- `auth.test.ts`: `needs the password as well as the link, so a mailbox owner cannot activate a foreign registration`,
  `lets the next registration replace the password of an unverified account`
- `verification.test.ts`: `keeps legacy accounts out until they prove their mailbox, and the seeded admin trusted`

## Konsep singkat

Skenario serangan pada versi starter:

1. Penyerang mendaftarkan `korban@contoh.id` dengan password pilihannya.
2. Korban menerima email "Verifikasi email Anda", mengira ia lupa pernah mendaftar,
   lalu mengklik tautannya.
3. Akun aktif, tetapi password-nya milik **penyerang**. Penyerang kini bisa masuk ke akun
   yang tercatat atas nama alamat email korban, dan menunggu korban mengisinya dengan
   alamat dan pesanan.

Syarat yang benar adalah **keduanya**:

| Yang dimiliki                     | Bisa mengaktifkan? |
| --------------------------------- | ------------------ |
| tautan saja (pemilik kotak surat) | tidak              |
| password saja (pendaftar)         | tidak              |
| tautan **dan** password           | ya                 |

Lima password salah pada satu tautan membuat tautan itu hangus. Penghitungnya harus
tersimpan walau request-nya gagal, jadi kesalahan **tidak boleh** dilempar di dalam
transaksi (transaksi yang gagal membatalkan penghitungnya juga).

## Langkah-langkah

### Langkah 1 — Impor dan tanda tangan

Kembalikan `matchingPasswordHash` ke impor dari `./users.ts`, dan ganti parameter
`_password` menjadi `password`.

`matchingPasswordHash(userId, password)` (sudah ada di `users.ts`) selalu menjalankan
satu `bcrypt.compare`, juga untuk akun yang tidak ada, dan mengembalikan hash password
bila cocok atau `null` bila tidak.

### Langkah 2 — Isi `verifyEmail`

```ts
const key = hash(token);
const record = pending.get(key);
if (!record || record.expiresAt <= now) throw invalid();
const passwordHash = await matchingPasswordHash(record.userId, password); // di LUAR transaksi: bcrypt lambat

const outcome = database.transaction((): PublicUser | 'invalid' | 'wrong-password' => {
  const current = pending.get(key); // baca ulang: bisa sudah dipakai
  if (!current || current.expiresAt <= now) return 'invalid';
  const user = passwordHash === null ? null : markEmailVerified(current.userId, passwordHash);
  if (!user) {
    const attempts = (current.attempts ?? 0) + 1;
    if (attempts >= config.emailVerification.maxPasswordAttempts) pending.delete(key);
    else pending.set(key, { ...current, attempts });
    return 'wrong-password';
  }
  forgetVerifications(current.userId); // tautan lain akun ini ikut hangus
  return user;
});
if (outcome === 'invalid') throw invalid();
if (outcome === 'wrong-password')
  throw new AppError(401, 'Password salah', undefined, 'INVALID_CREDENTIALS');
return outcome;
```

`markEmailVerified(id, expectedPasswordHash)` hanya berhasil bila password akun **masih**
sama dengan yang tadi dicocokkan. Bila di antara kedua langkah seseorang mendaftar
ulang dan mengganti password-nya (m12.8), verifikasi ini ditolak.

### Langkah 3 — Lihat sisi frontend

`frontend/src/pages/VerifyEmailPage.tsx` membaca token dari fragment URL
(`#token=...`, tidak pernah dikirim ke server lewat URL), lalu meminta password sebelum
memanggil `POST /api/v1/auth/verify-email`. Coba alurnya di browser lewat kotak surat
pelatihan.

## Kriteria lulus

- [ ] Ketiga tes di atas lulus; tidak ada tes lain yang gagal.
- [ ] Tautan tanpa password, atau dengan password salah, tidak mengaktifkan akun.
- [ ] Setelah lima password salah, tautan itu tidak bisa dipakai lagi.

## Bila ada masalah

| Gejala                                             | Solusi                                                                                |
| -------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Penghitung percobaan tidak pernah bertambah        | Anda melempar error di dalam transaksi; kembalikan hasil lalu lempar di luar.         |
| Transaksi mengeluh "callbacks must be synchronous" | `await` tidak boleh berada di dalam `database.transaction`. Hitung bcrypt sebelumnya. |
| Password lama pendaftar pertama masih berlaku      | `markEmailVerified` harus diberi `passwordHash` yang dicocokkan.                      |
