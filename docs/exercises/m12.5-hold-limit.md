Tes yang gagal (`tests/orders-relational.test.ts`, blok _per-customer hold limit_):

- `caps the number of open orders per customer`
- `caps the units of one product a customer holds in open orders`
- `aggregates duplicate lines before applying the per-product limit`
- `keeps cancellation requests inside the limit until stock is actually released`
- `cannot be bypassed with parallel requests`

## Konsep singkat

Dua batas, keduanya dari `config.holdLimit` (bisa diubah lewat environment):

| Batas                     | Bawaan | Variabel environment          |
| ------------------------- | ------ | ----------------------------- |
| pesanan aktif per akun    | 5      | `ORDER_MAX_OPEN_ORDERS`       |
| unit satu produk per akun | 10     | `ORDER_MAX_UNITS_PER_PRODUCT` |

"Aktif" berarti pesanan yang masih menahan stok: `PENDING`, `CONFIRMED`, atau
`CANCELLATION_REQUESTED` (stoknya belum benar-benar kembali), dan belum `COMPLETED`.
Data itu sudah disediakan `heldByCustomer(userId)` di `order-table.ts`.

## Langkah-langkah

### Langkah 1 — Tulis `assertWithinHoldLimit(userId, input)`

```ts
const { maxOpenOrders, maxUnitsPerProduct } = config.holdLimit;
const held = heldByCustomer(userId);
if (held.openOrders >= maxOpenOrders)
  throw new AppError(
    409,
    `Maksimal ${maxOpenOrders} pesanan aktif. ...`,
    { limit: maxOpenOrders, open: held.openOrders },
    'HOLD_LIMIT_EXCEEDED',
  );
for (const { productId, quantity } of input) {
  const already = held.units.get(productId) ?? 0;
  if (already + quantity > maxUnitsPerProduct)
    throw new AppError(
      409,
      `Maksimal ${maxUnitsPerProduct} unit per produk dalam pesanan aktif.`,
      { productId, limit: maxUnitsPerProduct, held: already, requested: quantity },
      'HOLD_LIMIT_EXCEEDED',
    );
}
```

Ganti nama parameter `_userId`/`_input` menjadi `userId`/`input`.

### Langkah 2 — Pahami di mana fungsi ini dipanggil

Buka `createOrder` di berkas yang sama. `assertWithinHoldLimit` dipanggil:

- **di dalam** `database.transaction`, tepat sebelum `insertOrderRow`. SQLite menjalankan
  penulisan satu per satu, jadi dua request paralel tidak bisa sama-sama lolos;
- **sesudah** pemeriksaan `Idempotency-Key`. Retry dengan key yang sudah dikenal
  dijawab dengan pesanan lama, sehingga tidak pernah ditolak oleh batas;
- dengan `input` yang **sudah digabung per produk**. Dua baris produk yang sama dalam
  satu request dihitung sebagai jumlahnya.

## Bila ada masalah

| Gejala                               | Solusi                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------- |
| Request paralel lolos bersama        | Pemeriksaan harus di dalam transaksi yang sama dengan insert order.    |
| Retry ditolak                        | Jangan memindahkan pemanggilan ke sebelum pemeriksaan idempotency key. |
| Dua baris produk sama tidak dijumlah | Pakai `input` (sudah digabung), bukan `items` dari body.               |
