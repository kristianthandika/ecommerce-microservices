# m12.4 — Order dari Blob JSON ke Tabel Relasional

| Branch awal                       | Kunci jawaban                      | Waktu     | Sebelumnya | Berikutnya |
| --------------------------------- | ---------------------------------- | --------- | ---------- | ---------- |
| `starter/m12.4-relational-orders` | `solution/m12.4-relational-orders` | 150 menit | m12.3      | m12.5      |

## Yang akan Anda pelajari

- Mengapa "ambil semua lalu filter di JavaScript" tidak bertahan saat data tumbuh.
- Merancang tabel dan indeks dari query yang benar-benar dijalankan.
- **Migrasi skema** yang aman: memindahkan data lama tanpa kehilangan satu field pun.
- **Keyset pagination** (cursor) yang tidak mengulang dan tidak melewati baris.

## Kondisi awal

- `services/order-service/src/migrations.ts`: daftar migrasi **kosong**.
- `services/order-service/src/order-table.ts`: setiap fungsi membaca **semua** order dari
  key/value store (`database.store('orders')`) lalu memfilter dan mengurutkan di
  JavaScript. Hasilnya benar, tetapi biayanya tumbuh linear. Cursor belum didukung.

Tanda tangan fungsi di `order-table.ts` sudah final, jadi `orders.ts` dan route tidak
perlu diubah.

```bash
git switch starter/m12.4-relational-orders
npm ci && npm run build:packages
npm test --workspace=services/order-service
```

Tes yang gagal (`tests/orders-relational.test.ts`):

- `moves legacy order records into tables, keeping every field`
- `answers list, recovery and admin queries from indexes`
- `pages with a keyset cursor that neither repeats nor skips when orders arrive`

## Konsep singkat

| Query                                    | Kolom yang dibutuhkan                         | Indeks                                |
| ---------------------------------------- | --------------------------------------------- | ------------------------------------- |
| riwayat pelanggan, terbaru dulu          | `user_id`, `created_at`, `id`                 | `(user_id, created_at DESC, id DESC)` |
| antrean recovery (PENDING, terlama dulu) | `status`, `created_at`, `id`                  | `(status, created_at, id)`            |
| daftar admin, terbaru dulu               | `created_at`, `id`                            | `(created_at DESC, id DESC)`          |
| ringkasan admin                          | `status`, `fulfillment_status`, `total`       | (scan; tabelnya kecil per baris)      |
| batas tahan per pelanggan (m12.5)        | `order_lines(order_id, product_id, quantity)` | primary key                           |

Yang perlu difilter, diurutkan, atau dijumlahkan menjadi **kolom**. Sisanya (snapshot
item, alamat, data pembatalan) tetap JSON di kolom `details`. Jangan menyimpan field
yang sama di kolom **dan** di JSON: kolom adalah sumber kebenaran.

**Mengapa cursor, bukan `OFFSET`?** `OFFSET 10000` memaksa database membaca lalu
membuang 10.000 baris. Pesanan baru yang masuk di antara dua halaman juga menggeser
semua baris, sehingga ada yang muncul dua kali. Cursor menyimpan posisi terakhir
`(created_at, id)` dan meminta baris "sebelum posisi itu".

## Langkah-langkah

### Langkah 1 — Migrasi `order-001-relational-orders`

Di `migrations.ts`, satu entri `{ name: 'order-001-relational-orders', up: (db) => db.exec(sql) }`.
Isi SQL-nya:

1. `CREATE TABLE orders (id TEXT PRIMARY KEY, user_id TEXT NOT NULL, status TEXT NOT NULL CHECK (status IN (...)), fulfillment_status TEXT NOT NULL DEFAULT 'NEW' CHECK (...), total INTEGER NOT NULL CHECK (total >= 0), recipient TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL, details TEXT NOT NULL CHECK (json_valid(details))) STRICT;`
2. Tiga indeks dari tabel di atas.
3. `CREATE TABLE order_lines (order_id TEXT NOT NULL REFERENCES orders (id) ON DELETE CASCADE, product_id TEXT NOT NULL, quantity INTEGER NOT NULL CHECK (quantity > 0), PRIMARY KEY (order_id, product_id)) STRICT, WITHOUT ROWID;`
4. Pindahkan data: `INSERT INTO orders (...) SELECT key, json_extract(value, '$.userId'), ... , json_remove(value, '$.id', '$.userId', '$.status', ...) FROM records WHERE namespace = 'orders';`
5. Isi `order_lines` dari `$.input` (atau `$.items` untuk order sangat lama) dengan
   `json_each`, dijumlahkan per produk.
6. `DELETE FROM records WHERE namespace = 'orders';`

`packages/storage` menjalankan setiap migrasi dalam transaksinya sendiri, mencatatnya
di tabel `schema_migrations`, dan membuat backup `*.pre-order-001-...bak` sebelum
menyentuh data yang ada.

### Langkah 2 — Tulis ulang `order-table.ts` dengan SQL

Semua lewat `database.statement(sql)` dengan parameter `?`. **Jangan** menyisipkan nilai
ke string SQL.

| Fungsi                     | Isi                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fromRow` / `details`      | gabungkan kolom dengan `JSON.parse(row.details)`; sebaliknya buang field yang sudah jadi kolom                                                   |
| `getOrderRow(id)`          | `SELECT * FROM orders WHERE id = ?`                                                                                                              |
| `insertOrderRow(o, lines)` | satu transaksi: `INSERT INTO orders ...` lalu satu `INSERT INTO order_lines` per baris                                                           |
| `updateOrderRow(o)`        | `UPDATE orders SET ... WHERE id = ?`; `changes !== 1` → lempar error                                                                             |
| `unfinishedOrders(limit)`  | `WHERE status IN ('PENDING','CANCELLATION_REQUESTED') ORDER BY created_at, id LIMIT ?`                                                           |
| `pageOrders(query)`        | `WHERE` dari `userId`/`status`/`q`, `count(*)` untuk `total`, lalu `LIMIT ? OFFSET ?`; ambil `limit + 1` baris untuk tahu ada halaman berikutnya |
| `orderSummary()`           | `SELECT status, fulfillment_status, count(*), sum(total) ... GROUP BY ...`                                                                       |
| `heldByCustomer(userId)`   | `count(*)` order terbuka dan `sum(quantity)` per produk dari `JOIN order_lines`                                                                  |
| `clearOrderRows()`         | `DELETE FROM orders` (baris `order_lines` ikut terhapus lewat `ON DELETE CASCADE`)                                                               |

"Terbuka" untuk `heldByCustomer` berarti status `PENDING`, `CONFIRMED`, atau
`CANCELLATION_REQUESTED`, dan `fulfillment_status <> 'COMPLETED'`.

### Langkah 3 — Cursor

`encodeCursor` sudah ada. Tambahkan `decodeCursor(cursor)`: base64url → JSON → harus
array berisi dua string (masing-masing paling panjang 64 karakter); selain itu
`AppError(400, 'Cursor tidak valid', undefined, 'INVALID_CURSOR')`. Di `pageOrders`,
bila ada cursor tambahkan `(created_at, id) < (?, ?)` ke `WHERE` dan pakai `OFFSET 0`.
`nextCursor` = `encodeCursor(baris terakhir)` bila hasilnya lebih dari `limit`.

## Kriteria lulus

- [ ] Ketiga tes di atas lulus; tidak ada tes lain yang gagal.

## Bila ada masalah

| Gejala                             | Solusi                                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| Indeks tidak dipakai               | Urutan kolom indeks harus mengikuti `WHERE` lalu `ORDER BY`.                                  |
| Halaman berikutnya mengulang order | Pembanding cursor harus baris `(created_at, id) < (?, ?)`, bukan hanya `created_at`.          |
| Migrasi gagal di tengah            | Satu migrasi = satu transaksi; perbaiki SQL lalu jalankan ulang tes (database tes di memory). |
| Status di kolom dan JSON berbeda   | `details()` harus membuang field yang sudah menjadi kolom.                                    |
