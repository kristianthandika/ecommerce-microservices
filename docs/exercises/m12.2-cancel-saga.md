# m12.2 — Pembatalan Order sebagai Saga

| Branch awal                 | Kunci jawaban                | Waktu     | Sebelumnya | Berikutnya |
| --------------------------- | ---------------------------- | --------- | ---------- | ---------- |

## Yang akan Anda pelajari

- Membatalkan pesanan yang melibatkan **dua service** tanpa transaksi terdistribusi.
- Saga: simpan **niat** secara durable dulu, lalu jalankan **kompensasi** (kembalikan stok).
- Kompensasi yang **idempoten** dan _tombstone_ untuk reservasi yang datang terlambat.

## Kondisi awal

Dua fungsi menjawab `501 NOT_IMPLEMENTED`:

- `releaseReservation` di `services/product-service/src/products.ts`
- `cancelOrder` di `services/order-service/src/orders.ts`

```bash
git switch starter/m12.2-cancel-saga

npm test --workspace=services/product-service --workspace=services/order-service
```

Tes yang gagal di starter dan harus lulus:

- product-service (`tests/inventory.test.ts`): `returns stock once, even when released repeatedly`,
  `tombstones an unknown ID so a late reserve request cannot take stock`,
  `bumps the product revision so stale admin edits are rejected after a release`
- order-service (`tests/cart-cancel.test.ts` dan `tests/orders-relational.test.ts`):
  `lets the owner cancel a new order, restocks once and hides it from others`,
  `leaves processing orders to administrators and refuses completed or failed ones`,
  `finishes a cancellation requested during an outage once product-service is back`,
  `never lets a reservation that lost the race against a cancellation take stock`,
  `forgets keys of settled orders after the retention window, never of pending ones`,
  `keeps cancellation requests inside the limit until stock is actually released`,
  `caps the units of one product a customer holds in open orders`

## Konsep singkat

```
pelanggan ── POST /orders/:id/cancel ──▶ order-service
   1. (transaksi lokal) status := CANCELLATION_REQUESTED          ← niat tersimpan
   2. POST /internal/reservations/:id/release ──▶ product-service
         (transaksi lokal) stok += jumlah, receipt := RELEASED     ← kompensasi
   3. (transaksi lokal) status := CANCELLED
   bila langkah 2 gagal (product-service mati): jawab 202; recovery mengulang langkah 2–3
```

Tidak ada satu transaksi yang mencakup dua database. Ketahanannya datang dari tiga
sifat: niat tersimpan sebelum memanggil service lain, kompensasi boleh diulang tanpa
efek ganda, dan proses recovery (`recoverPendingOrders`) menyelesaikan sisanya.

**Tombstone.** Bayangkan pesanan dibatalkan **sebelum** reservasi stoknya sampai di
product-service (respons hilang, request tertunda). Bila product-service tidak
mencatat apa pun, reservasi yang datang belakangan akan mengambil stok untuk pesanan
yang sudah batal. Karena itu pelepasan untuk ID yang belum dikenal menulis receipt
`RELEASED` kosong, dan `reserveStock` menolak ID yang sudah `RELEASED`.

## Langkah-langkah

### Langkah 1 — `releaseReservation(id)` di product-service

Semua di dalam **satu** `database.transaction(() => { ... })`:

1. `const existing = reservations.get(id)`.
2. Tidak ada → simpan tombstone
   `{ id, fingerprint: '', items: [], total: 0, status: 'RELEASED', releasedAt }`
   dengan `reservations.insert`, lalu kembalikan.
3. Sudah `RELEASED` → kembalikan apa adanya (idempoten).
4. Selain itu → untuk setiap baris `adjustStock(line.productId, line.quantity)`, lalu
   simpan `{ ...existing, status: 'RELEASED', releasedAt }`.

`adjustStock` menaikkan `revision` produk, sehingga admin yang menyimpan data produk
dari tampilan lama ditolak.

Jalankan tes product-service; ketiga tesnya lulus.

### Langkah 2 — `cancelOrder(id, actor, reason, ctx)` di order-service

Fase 1, dalam transaksi:

1. `getOrderRow(id)`. Tidak ada, **atau** `actor.role === 'customer'` dan pemiliknya
   bukan `actor.userId` → `AppError(404, 'Order tidak ditemukan', undefined, 'NOT_FOUND')`.
   Jawaban yang sama untuk "tidak ada" dan "milik orang lain" mencegah penebakan ID.
2. Sudah `CANCELLATION_REQUESTED` atau `CANCELLED` → kembalikan order itu (idempoten).
3. `FAILED` → 409 `ORDER_NOT_CANCELLABLE` (tidak ada stok yang perlu dilepas).
4. `fulfillmentStatus` `COMPLETED` → 409 `ORDER_NOT_CANCELLABLE`. Pelanggan juga ditolak
   bila fulfillment sudah bukan `NEW` ("Hubungi admin").
5. Simpan dengan `updateOrderRow`: `status: 'CANCELLATION_REQUESTED'`,
   `cancelledBy: actor.role`, `cancelReason`, `updatedAt`.

Fase 2, di luar transaksi:

```ts
if (requested.status === 'CANCELLED') return { order: publicOrder(requested), completed: true };
try {
  const order = await release(requested, ctx); // sudah ada di berkas ini
  return { order, completed: order.status === 'CANCELLED' };
} catch (err) {
  if (err instanceof AppError && err.status >= 500)
    // product-service tidak terjangkau
    return { order: publicOrder(getOrderRow(id)!), completed: false }; // route menjawab 202
  throw err;
}
```

Pelajari fungsi `release()` yang sudah ada: ia memanggil product-service, lalu menulis
`CANCELLED` hanya bila status masih `CANCELLATION_REQUESTED`.

## Bila ada masalah

| Gejala                                  | Solusi                                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Stok kembali dua kali                   | Pemeriksaan status `RELEASED` dan penambahan stok harus di transaksi yang sama.                                     |
| Stok bocor setelah batal                | Tombstone tidak ditulis untuk ID yang belum dikenal.                                                                |
| Order tertahan `CANCELLATION_REQUESTED` | Recovery melanjutkan status ini lewat `release()`; pastikan status itu tersimpan sebelum memanggil product-service. |
| 500 saat product-service mati           | Error 5xx dari release berarti "belum selesai": kembalikan `completed: false` (202).                                |
