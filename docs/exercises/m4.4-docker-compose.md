# m4.4 — Orkestrasi dengan Docker Compose

| Branch awal                   | Kunci jawaban                  | Waktu    | Sebelumnya | Berikutnya |
| ----------------------------- | ------------------------------ | -------- | ---------- | ---------- |
| `starter/m4.4-docker-compose` | `solution/m4.4-docker-compose` | 90 menit | m4.3       | m4.5       |

## Yang akan Anda pelajari

- Menjalankan lima container dengan satu perintah.
- Urutan start yang benar dengan `healthcheck` dan `depends_on: condition: service_healthy`.
- Jaringan internal: hanya gateway dan frontend yang terlihat dari laptop.
- Volume untuk data yang harus bertahan saat container dibuat ulang (kunci RSA).

## Kondisi awal

Kelima image bisa di-build sendiri-sendiri (m4.3), tetapi belum saling terhubung.

```bash
git switch starter/m4.4-docker-compose
npm ci
```

**Sebelum mulai:** Compose memakai port **3000** dan **8080** di laptop Anda. Hentikan
`npm run dev:all` dan stack Docker lain dari repo ini (`docker compose down` di folder
mana pun tempat Anda pernah menjalankannya). Nama proyek Compose di sini adalah
`ecommerce-microservices`; stack lain dengan nama yang sama akan **digantikan**.

## Konsep singkat

`depends_on` biasa hanya menunggu container **dibuat**, bukan **siap**. auth-service
butuh beberapa detik untuk membuat kunci RSA; bila product-service mulai lebih dulu
dan langsung mengambil JWKS, ia gagal. Dengan `condition: service_healthy`, Compose
menunggu sampai healthcheck auth-service lulus.

Di dalam jaringan Docker, service saling memanggil dengan **nama service**
(`http://auth-service:3001`), bukan `localhost`. Karena alamat dibaca dari
environment (m0.1), Compose cukup mengubah variabelnya, tanpa mengubah kode.

## Langkah-langkah

### Langkah 1 — Kerangka `docker-compose.yml`

```yaml
name: ecommerce-microservices

x-healthcheck-defaults: &healthcheck-defaults
  interval: 5s
  timeout: 3s
  retries: 5
  start_period: 8s

services:
  # ... diisi di langkah berikut

volumes:
  auth-keys:

networks:
  internal:
    driver: bridge
```

`x-healthcheck-defaults` adalah _anchor_ YAML: pengaturan yang ditulis sekali lalu
dipakai ulang dengan `<<: *healthcheck-defaults`.

### Langkah 2 — auth-service

```yaml
auth-service:
  build:
    context: .
    dockerfile: services/auth-service/Dockerfile
  environment:
    - PORT=3001
    - LOG_LEVEL=${LOG_LEVEL:-info}
    - CORS_ORIGIN=${FRONTEND_ORIGIN:-http://localhost:3000}
    - SEED_ADMIN_EMAIL=${SEED_ADMIN_EMAIL:-admin@inixindo.local}
    - SEED_ADMIN_PASSWORD=${SEED_ADMIN_PASSWORD:-admin123}
  volumes:
    - auth-keys:/app/services/auth-service/keys # kunci RSA bertahan saat restart
  healthcheck:
    test:
      [
        'CMD',
        'node',
        '-e',
        "fetch('http://localhost:3001/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))",
      ]
    <<: *healthcheck-defaults
  networks: [internal]
```

Healthcheck memakai `node -e fetch(...)` karena image Alpine Node tidak punya `curl`.
Tidak ada `ports:` di sini: auth-service tidak bisa dijangkau dari laptop.

### Langkah 3 — product-service dan order-service

Sama seperti auth-service, dengan:

- product-service: `AUTH_SERVICE_URL=http://auth-service:3001`, `depends_on: auth-service: condition: service_healthy`.
- order-service: ditambah `PRODUCT_SERVICE_URL=http://product-service:3002`, dan
  menunggu auth-service **serta** product-service sehat.

### Langkah 4 — gateway

```yaml
gateway:
  build: { context: ., dockerfile: services/gateway/Dockerfile }
  environment:
    - PORT=8080
    - AUTH_SERVICE_URL=http://auth-service:3001
    - PRODUCT_SERVICE_URL=http://product-service:3002
    - ORDER_SERVICE_URL=http://order-service:3003
    - CORS_ORIGIN=${FRONTEND_ORIGIN:-http://localhost:3000}
  depends_on:
    auth-service: { condition: service_healthy }
    product-service: { condition: service_healthy }
    order-service: { condition: service_healthy }
  healthcheck:
    test:
      [
        'CMD',
        'node',
        '-e',
        "fetch('http://localhost:8080/').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))",
      ]
    <<: *healthcheck-defaults
  ports: ['8080:8080']
  networks: [internal]
```

Healthcheck gateway memakai `GET /`, bukan `/health`. `/health` menjawab 503 bila ada
service lain yang mati, padahal gateway-nya sendiri sehat.

### Langkah 5 — frontend

```yaml
frontend:
  build:
    context: .
    dockerfile: frontend/Dockerfile
    args:
      VITE_API_BASE_URL: ${VITE_API_BASE_URL:-http://localhost:8080}
  depends_on:
    gateway: { condition: service_healthy }
  healthcheck:
    test: ['CMD', 'wget', '-qO-', 'http://127.0.0.1:80/']
    <<: *healthcheck-defaults
  ports: ['3000:80']
  networks: [internal]
```

Dua jebakan di sini:

- `VITE_API_BASE_URL` adalah alamat yang dipakai **browser di laptop Anda**, jadi
  `http://localhost:8080`, bukan `http://gateway:8080`. Browser tidak mengenal nama
  service Docker.
- Healthcheck memakai `127.0.0.1`, bukan `localhost`. `wget` di Alpine bisa mencoba
  IPv6 (`::1`) untuk `localhost`, sedangkan nginx hanya mendengarkan IPv4.

### Langkah 6 — Jalankan

```bash
docker compose config --quiet          # periksa sintaks; tanpa keluaran = benar
docker compose up --build -d
docker compose ps                      # tunggu semua "healthy"
```

Buka http://localhost:3000, login dengan `admin@inixindo.local` / `admin123`.

## Menguji hasil kerja

```bash
curl -s localhost:8080/health                    # semua "up"
curl -s --max-time 2 localhost:3001/health       # GAGAL: auth-service tidak terbuka ke laptop
docker compose logs gateway | tail -5            # log JSON gateway
```

**Restart tidak membatalkan token:**

1. Login lewat frontend; dashboard menampilkan katalog.
2. `docker compose restart auth-service`, lalu tunggu `healthy`.
3. Muat ulang katalog di dashboard. Token lama masih diterima, karena kunci RSA dibaca
   dari volume `auth-keys`, tidak dibuat ulang. (Pengguna yang didaftarkan sendiri
   hilang setelah restart, karena penyimpanannya masih di memory. Itu diperbaiki di
   materi lanjutan.)

**Tanpa race condition:** jalankan `docker compose down && docker compose up -d`
beberapa kali. Setiap kali, semua container harus mencapai `healthy` tanpa ada yang
restart.

Tes unit tetap harus lulus: `npm test` (35 tes).

## Kriteria lulus

- [ ] `docker compose up --build -d` dari clone bersih menghasilkan lima container `healthy`.
- [ ] Hanya port 3000 dan 8080 yang terbuka ke laptop.
- [ ] Login dari frontend berhasil; restart auth-service tidak membatalkan token.
- [ ] Hentikan dengan `docker compose down` (tambah `-v` hanya bila ingin menghapus kunci RSA).

## Bila ada masalah

| Gejala                                     | Solusi                                                                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Service gagal terhubung padahal "up"       | Ganti `depends_on` biasa dengan `condition: service_healthy`.                                                                                |
| Frontend: "Tidak dapat menghubungi server" | `VITE_API_BASE_URL` harus `http://localhost:8080` dan ditanam saat build. Setelah mengubahnya, build ulang: `docker compose build frontend`. |
| `port is already allocated`                | Port 3000/8080 dipakai proses lain (`npm run dev`, stack lain). Hentikan dulu.                                                               |
| frontend tidak pernah `healthy`            | Healthcheck memakai `localhost`; ganti dengan `127.0.0.1`.                                                                                   |
| Token tidak berlaku setelah restart        | Volume `auth-keys` tidak terpasang ke `/app/services/auth-service/keys`.                                                                     |
