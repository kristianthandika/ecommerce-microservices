## Yang akan Anda pelajari

- Masalah klasik JWT: token tetap sah sampai kedaluwarsa, walau pengguna sudah logout.
- Menutupnya tanpa membuang keuntungan verifikasi lokal: **daftar pencabutan** yang di-cache.
- Prinsip **fail closed**: tanpa data yang segar, tolak (503), jangan menerima.

## Kondisi awal

auth-service sudah mencabut sesi saat logout (m12.3) dan menerbitkan daftar `sid` yang
dicabut di route internal `GET /internal/revocations` (butuh service token). Namun
product-service dan order-service **menerima semua sesi**: `createRevocationChecker`
di kedua berkas berikut hanya mengembalikan `false`.

- `services/product-service/src/middleware/revocations.ts`
- `services/order-service/src/middleware/revocations.ts` (salinan yang sama persis)

```bash

npm test --workspace=services/product-service --workspace=services/order-service
```

Tes yang gagal:

- order-service (`tests/session-revocation.test.ts`): `refuses a revoked session within the refresh window, and only that session`,
  `denies known revoked sessions and fails closed for others when the list is stale`,
  `fails closed on the first fetch failure and coalesces concurrent callers during cooldown`,
  `waits for a refresh when stale, shares it, and backs off after a failure`
- product-service (`tests/session-revocation.test.ts`): `refuses an administrator token after its session was revoked`,
  `keeps working when many sessions were revoked (a list larger than 1 MiB)`

## Konsep singkat

Setiap access token membawa klaim `sid` (ID keluarga sesi). Saat logout, auth-service
memasukkan `sid` itu ke daftar pencabutan **selama access token terakhirnya masih bisa
berlaku** (paling lama 15 menit ditambah 1 menit toleransi jam). Daftarnya pendek.

Service lain tidak bertanya ke auth-service di setiap request. Mereka menyimpan seluruh
daftar di memory dan memperbaruinya paling lama setiap `REVOCATION_MAX_AGE_MS` (bawaan
5 detik). Jadi logout berlaku di semua service dalam beberapa detik.

| Situasi                                  | Jawaban `isRevoked(sid)`                             |
| ---------------------------------------- | ---------------------------------------------------- |
| `sid` sudah pernah terlihat dicabut      | `true`, tanpa jaringan sama sekali                   |
| daftar masih segar (< `maxAgeMs`)        | jawab dari memory                                    |
| daftar sudah tua                         | **tunggu** refresh dulu, lalu jawab                  |
| refresh gagal dan tidak ada daftar segar | lempar 503 `SESSION_CHECK_UNAVAILABLE` (fail closed) |

Tiga detail penting:

- **Satu fetch untuk semua.** Seratus request bersamaan saat daftar kedaluwarsa hanya
  boleh memicu **satu** fetch; yang lain menunggu promise yang sama.
- **Jeda setelah gagal.** Setelah fetch gagal, jangan mencoba lagi sebelum `cooldownMs`
  lewat; tanpa jeda, auth-service yang sedang sakit dibanjiri.
- **Waktu fetch dicatat saat fetch dimulai**, bukan saat selesai. Pencabutan yang
  terjadi selama fetch berlangsung tidak boleh dianggap sudah terlihat.

## Langkah-langkah

### Langkah 1 — State di closure

```ts
export function createRevocationChecker(
  fetchRevoked: () => Promise<Iterable<string>>,
  { maxAgeMs = 5000, cooldownMs = 5000, now = Date.now, onError }: RevocationCheckerOptions = {},
): (sid: string) => Promise<boolean> {
  let revoked = new Set<string>();
  let fetchedAt: number | undefined; // refresh terakhir yang BERHASIL
  let failedAt: number | undefined;
  let refreshing: Promise<void> | undefined;
  // ...
}
```

Kembalikan `import { AppError } from './errors.ts';` di bagian atas berkas (starter
menghapusnya karena belum dipakai).

### Langkah 2 — Fungsi `refresh()` yang dibagi bersama

```ts
function refresh(): Promise<void> {
  if (!refreshing) {
    const startedAt = now();
    refreshing = Promise.resolve()
      .then(fetchRevoked)
      .then((next) => {
        revoked = new Set(next);
        fetchedAt = startedAt;
        failedAt = undefined;
      })
      .catch((err: unknown) => {
        failedAt = now();
        onError?.(err);
      })
      .finally(() => {
        refreshing = undefined;
      });
  }
  return refreshing;
}
```

### Langkah 3 — Fungsi yang dikembalikan

```ts
return async (sid) => {
  if (revoked.has(sid)) return true;
  const fresh = fetchedAt !== undefined && now() - fetchedAt < maxAgeMs;
  if (!fresh) {
    const failedRecently = failedAt !== undefined && now() - failedAt < cooldownMs;
    if (refreshing || !failedRecently) await refresh();
  }
  if (revoked.has(sid)) return true;
  if (fetchedAt === undefined || now() - fetchedAt >= maxAgeMs)
    throw new AppError(
      503,
      'Status sesi belum dapat diverifikasi. Coba lagi sebentar.',
      undefined,
      'SESSION_CHECK_UNAVAILABLE',
    );
  return false;
};
```

## Bila ada masalah

| Gejala                                           | Solusi                                                                             |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Banyak fetch untuk banyak request bersamaan      | `refresh()` harus mengembalikan promise yang sama selama `refreshing` terisi.      |
| Sesi yang dicabut kadang lolos                   | `fetchedAt` diisi dengan waktu **selesai** fetch; pakai waktu **mulai**.           |
| 503 terus-menerus padahal auth-service hidup     | `failedAt` tidak dikosongkan setelah fetch berhasil.                               |
| Token ditolak setelah auth-service mati sebentar | Itu disengaja (fail closed). Sesi yang sudah dicabut tetap ditolak tanpa jaringan. |
